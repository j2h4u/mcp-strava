## Summary

This phase converts five categories of SQLite-era residuals in the DuckDB adapter to native DuckDB types and SQL idioms. The DB is regenerated from source (resync + read-model rematerialization) so every schema change is a DDL edit + recreate — no ALTER-migration of an existing DB, no compat shims.

The most important mechanic to understand is the **two-tier schema creation**. Regular tables (including the three `missing_reasons_json` tables and `streams`) live in `DUCKDB_SCHEMA_SQL` and are created once by `create_schema()` — no in-place migration. `activity_metric_facts` is different: it is DDL-generated by the metric registry (`activity_metric_facts_table_sql()`) and is also created inside `DUCKDB_SCHEMA_SQL` via an f-string embed. Changing a column's `sql_type` in `_MATERIALIZED_FACT_COLUMN_SQL_METADATA` changes the generated CREATE TABLE — no separate ALTER step.

The fingerprint auto-recompute means Task 3's `cardiac_drift_significant` type change in `metric_registry_fact_column_sql.py` (a `COMPUTE_SOURCE_MODULES` member) auto-invalidates the read model on the next startup — correct by construction, but the planner must know this is expected behavior, not a regression.

**Primary recommendation:** Execute tasks in order 1 → 5. Each is an independent commit with its own `just check` + `pytest -n auto` gate. No task depends on another's code; all depend only on the DB being recreated fresh (which is the standard dev workflow).

## Schema Creation Mechanism (Critical for Planning)

**How the DB is created:** `create_schema(conn)` in `schema.py` executes `DUCKDB_SCHEMA_SQL` (a single large f-string in `schema_tables.py`) plus `create_aggregate_views(conn)`. There are no version-numbered migrations. The only in-place `ALTER TABLE ADD COLUMN IF NOT EXISTS` is in `refresh_state_store.py:36` for `last_full_summary_sync_at` — that is a one-off and unrelated to this phase.

**Consequence for all Tasks 1–4:** Schema changes are made by editing the DDL string in `schema_tables.py` (and `metric_registry_fact_column_sql.py` for `cardiac_drift_significant`). The old DB on disk is deleted and regenerated via resync + rematerialization. No migration code. No ALTER. This is intentional and matches the project's no-backward-compat principle.

**`activity_metric_facts` specifically (Phase 14 registry-owned schema):**
- DDL is generated at import time by `activity_metric_facts_table_sql()` in `metric_registry_fact_columns.py`.
- That function reads `_MATERIALIZED_FACT_COLUMN_SQL_METADATA["activity_metric_facts"]` from `metric_registry_fact_column_sql.py`.
- `_validate_fact_column_sql_metadata()` is called at module import — if `"BOOLEAN"` is not in `_SUPPORTED_FACT_SQL_TYPES` the service crashes on startup with a clear `ValueError`.
- The generated DDL is embedded into `DUCKDB_SCHEMA_SQL` via `{activity_metric_facts_table_sql()}`.
- For Task 3: add `"BOOLEAN"` to `_SUPPORTED_FACT_SQL_TYPES` (line 5), change `cardiac_drift_significant` entry from `_sql("BIGINT", nullable=False, default_sql="0")` to `_sql("BOOLEAN", nullable=False, default_sql="FALSE")`. But see the `_SUPPORTED_FACT_DEFAULT_SQL` constraint below.

```python
def _missing_reasons(row: dict[str, object]) -> list[str]:
    reasons: list[str] = []
    payloads = row.get("missing_reason_payloads")
    for payload in payloads if isinstance(payloads, list) else []:
        if payload is None:
            continue
        if isinstance(payload, list):
            reasons.extend(str(item) for item in payload if item)
        else:
            # Remove this branch after Task 4 is complete:

            if isinstance(parsed, list):

    return reasons
```

**`stream_coverage_queries.py:86-89` — Python loop → SQL predicate:**
Current (per-row Python json.loads loop):
```python
if not any(
    channel in (json.loads(str(item["values_json"])) if item["values_json"] else {})
    for item in value_rows
):
    missing_channels.append(channel)
```

Replacement SQL predicate (one query per channel, called inside the existing loop):
```python
exists_row = repo._fetchone(
    """
    SELECT 1 FROM streams
    WHERE activity_id = ?
      AND json_extract_string(values_json, '$.' || ?) IS NOT NULL
    LIMIT 1
    """,
    [activity_id, channel],
)
if exists_row is None:
    missing_channels.append(channel)
```
`json_extract_string(values_json, '$.' || ?)` works on a `VARCHAR` column in DuckDB — `json_extract_string` accepts any VARCHAR-typed expression as the JSON source. The `IS NOT NULL` predicate correctly identifies presence (a key with a null value would return NULL from json_extract_string, so only truly present non-null values match — this is equivalent to the Python `key in dict` check). [VERIFIED: DuckDB docs — json_extract_string on VARCHAR]

The `value_rows` fetch at lines 79-85 can be removed after this change (the `SELECT values_json FROM streams WHERE activity_id=?` query is replaced by the key-existence predicate).

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Date arithmetic from today | Custom Python date subtraction passed as string | `CURRENT_DATE - (? * INTERVAL '1 day')` in SQL | Native DuckDB — the whole point of this phase |
| Array flattening in Python | Loop over `payloads` calling json.loads | `list_distinct(flatten(list(col)))` in SQL | DuckDB array functions handle NULL, duplicates, flatten natively |
| Boolean conversion in Python | `int(bool_val)` or ternary `1 if x else 0` | Python `bool(x)` bound directly | DuckDB Python connector accepts Python bool for BOOLEAN columns |
| JSON key existence check | Fetch all rows, json.loads each one | `json_extract_string(col, '$.' || ?) IS NOT NULL` in SQL | Single SQL predicate, no Python deserialization |

## Common Pitfalls

### Pitfall 1: `_SUPPORTED_FACT_DEFAULT_SQL` blocks `"FALSE"` and `"[]"` (bare)
**What goes wrong:** Adding `BOOLEAN` to `_SUPPORTED_FACT_SQL_TYPES` but using `default_sql="FALSE"` for `cardiac_drift_significant` causes `_validate_fact_column_sql_metadata()` to raise `ValueError` at import time — service fails to start. Similarly, changing `missing_reasons_json` default from `"'[]'"` to `"[]"` (bare, no quotes) without adding `"[]"` to `_SUPPORTED_FACT_DEFAULT_SQL` causes the same crash.
**How to avoid:** Keep `cardiac_drift_significant` default as `"0"` (integer zero is valid for BOOLEAN in DuckDB, coerces to FALSE). Add `"[]"` to `_SUPPORTED_FACT_DEFAULT_SQL` for `VARCHAR[]` arrays.
**Warning signs:** `ValueError: ... has unsafe default_sql` at startup/import.

### Pitfall 2: `activities.date` read in `to_activity_row()` / `RepositoryActivityRow`
**What goes wrong:** `activity_lookup_queries.py` SELECT lists include `date` explicitly (lines 23, 37, 57). `to_activity_row()` in `activity_rows.py` builds a `RepositoryActivityRow` from the row dict. If `RepositoryActivityRow` has a `date` field, removing it from SELECT will cause a `KeyError` or missing-field error.
**How to avoid:** Read `activity_rows.py` before implementing Task 1; verify whether `RepositoryActivityRow` has a `.date` field and whether any caller uses it. If it does, remove the field and update callers.
**Warning signs:** `KeyError: 'date'` in tests or `mypy`/basedpyright error on `RepositoryActivityRow`.

### Pitfall 3: DATE column returns `datetime.date` object — comparison surprises
**What goes wrong:** Code that does `str(row["activity_day"]) >= "2026-01-01"` (string comparison) will continue to work after `activity_day` stays DATE (it already was DATE). But code that compares a DATE column result to a string literal in Python will break if it expects an exact type match. The `_coerce_day()` helper in `status_fact_queries.py` already handles both `datetime.date` and `str` — this is fine.
**For Task 2:** After `requested_for_day` becomes DATE, `str(row["requested_for_day"])` yields `"2026-05-21"` — same as before. Callers are safe.
**Warning signs:** Type errors in basedpyright for comparisons like `row["requested_for_day"] >= "..."`.

### Pitfall 4: `list()` aggregate on `VARCHAR[]` produces list-of-lists
**What goes wrong:** After `missing_reasons_json` becomes `VARCHAR[]`, `list(missing_reasons_json)` in aggregate SQL produces `list[list[str]]` (a list of arrays). The `_missing_reasons()` decoder currently calls `json.loads(str(payload))` on each element — `str(["a","b"])` is not valid JSON, so `json.loads` raises and the fallback `[str(payload)]` produces garbage.
**How to avoid:** Always use `list_distinct(flatten(list(missing_reasons_json)))` in the aggregate SQL so the result is already a flat `list[str]`. Then `_missing_reasons()` receives a flat list and only needs the `isinstance(payload, list)` branch.
**Warning signs:** `missing_reasons` appearing as `["['missing_hr']", ...]` in API responses.

### Pitfall 5: `is_moving` boolean read by metric computation code
**What goes wrong:** `stream_metric_queries.py` or other stream readers may filter `WHERE is_moving = 1` or `is_moving > 0`. After conversion to BOOLEAN, `= 1` still works in DuckDB (integer literals are coerced), but `is_moving > 0` is a type error on BOOLEAN. Python code doing `if row["is_moving"] == 1` will get `False` instead of the expected match because `False == 1` is `False` in Python (unlike `0 == False` which is `True`).
**How to avoid:** grep for `is_moving` reads in `stream_metric_queries.py` and update comparisons to `= TRUE` / `IS TRUE` in SQL and `is True` in Python.
**Warning signs:** `duckdb.InvalidInputException: Comparison between boolean and integer` or zero-valued metrics after conversion.

### Pitfall 6: The kudos `window_days` branch — `INTERVAL '1 day'` integer param
**What goes wrong:** Passing `f"-{window_days} days"` (string) to the new `? * INTERVAL '1 day'` expression causes a type mismatch (`InvalidInputException: Cannot multiply INTERVAL with VARCHAR`).
**How to avoid:** Bind a plain Python `int` (not a formatted string) for the interval multiplier: `params.append(window_days)` not `params.append(f"-{window_days} days")`.
