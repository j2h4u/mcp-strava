    Add three repository methods: current_logic_version() -> dict | None (SELECT metric_version, logic_fingerprint, changed_at FROM read_model_logic_version WHERE id=1; return None if table empty/absent); current_metric_version() -> int (return current_logic_version()'s metric_version, or fall back to the max metric_version present across fact tables, else 1, when the sidecar is unseeded — so reads never break on a partially-migrated DB; this fallback scans 4 UNION ALL'd fact tables, so cache the resolved value for the request/repo lifetime on the repo instance — a one-shot memoized attribute, e.g. self._current_metric_version_cache initialized to a sentinel like None and populated on first call — rather than re-scanning per call); bump_logic_version(metric_version: int, logic_fingerprint: str, changed_at: str) -> None (upsert the singleton row id=1).

    MEMO INVALIDATION (cycle-2 HIGH — REQUIRED): bump_logic_version() MUST invalidate the current_metric_version memo on the repo instance at the END of the bump (after the upsert commits) — reset the cache attribute to its sentinel (e.g. self._current_metric_version_cache = None). Rationale: the recompute path calls bump_logic_version(N+1, ...) and immediately afterward must see N+1 from current_metric_version() so the materialize and the enqueued dirty rows agree on the version. If the memo were populated to N before the bump and never cleared, current_metric_version() would keep returning the stale N, materialization would run at N while dirty rows are queued at N+1, and the self-invalidation would silently no-op. Clearing the memo inside bump_logic_version() is the single guaranteed point that closes this — do not rely on callers to reset it. Add a test asserting current_metric_version() reflects the new value immediately after bump_logic_version() on the SAME repo instance (memo does not serve the pre-bump value).

    Concrete DuckDB upsert form for the singleton: DuckDB does NOT honor SQLite `INSERT OR REPLACE` identically — use either `INSERT INTO read_model_logic_version (id, metric_version, logic_fingerprint, changed_at) VALUES (1, ?, ?, ?) ON CONFLICT (id) DO UPDATE SET metric_version=excluded.metric_version, logic_fingerprint=excluded.logic_fingerprint, changed_at=excluded.changed_at`, or a DELETE-then-INSERT of id=1 inside the same begin()/commit(). Pick the ON CONFLICT form (id is the PK).

    Extend _ensure_schema_extensions (195) to seed the sidecar idempotently: create the table if missing (CREATE TABLE IF NOT EXISTS read_model_logic_version ...), then if it has no row, INSERT a seed row with metric_version = (max metric_version present across fact tables, else 1) and logic_fingerprint = compute_logic_fingerprint() and changed_at = now. Seed=current by construction means the first refresh after deploy sees stored == live → no recompute.

    Seed-path robustness (review consensus): import compute_logic_fingerprint INSIDE the method (runtime) AND wrap the fingerprint computation in its own `try/except Exception` that logs a warning and skips seeding (leaving the sidecar unseeded → current_metric_version() falls back to the fact-table max/1 so reads stay safe). An ImportError or inspect.getsource OSError raised here is NOT a duckdb.CatalogException, so the existing CatalogException guard would NOT catch it — without this independent guard a transient import error breaks from_connection(). Keep the existing try/except duckdb.CatalogException guard for the schema-missing case; the fingerprint guard is a SEPARATE inner try/except Exception around only the compute_logic_fingerprint() call + seed INSERT.

    Unseeded-sidecar recovery (resolves the 15-02/15-03 contradiction — authoritative): in the NORMAL path this seed adopts-current, so the first refresh after deploy sees stored == live and does NOT recompute. If this seed is SKIPPED by the fingerprint guard above (a transient ImportError/OSError), adoption is NOT left to "next repo creation/restart": 15-03's materialize chokepoint owns an explicit `stored is None` → ADOPT-CURRENT branch that writes the sidecar (current/fallback version + live fingerprint, NO dirty enqueue) on the first cycle where all COMPUTE_SOURCE_MODULES are loaded. So adoption can happen EITHER here (seed, the common case) OR at the 15-03 chokepoint (self-heal after a transient seed failure); both write the same thing (stored = live, no recompute). This plan and 15-03 agree: seed-adopts-normally, chokepoint-adopts-on-recovery — they do not contradict.
